# Backup and restore

What to back up on a SkyLab server, how, and how to put it back. Machines themselves are backed up inside SkyLab (per-machine backups on Proxmox storage); this page is about the platform.

## What matters

| Item | Where | Why |
| --- | --- | --- |
| PostgreSQL database `app` | Docker volume `app-db-data`, service `db` | Users, requests, machines, classes, courses, firewall rules, settings, audit log, encrypted credentials. Without it SkyLab knows nothing about your machines. |
| `.env` | Repository root | `SECRET_KEY` decrypts the credentials in the database. A dump restored with a different key is useless. |
| LiteLLM database `litellm` and `vllm-service/litellm/.env` | Same PostgreSQL instance; file next to the compose include | AI API keys and model routing, when the AI stack is in use. |
| `vllm-service/models.json` | Repository | Model routing input for `prepare-ai-stack.sh`. |
| Gateway VM | The VM you provide | nginx rules and WireGuard peers are regenerated by SkyLab on "Sync"; the HTTPS certificate and private key are yours and are not stored in SkyLab. |
| Monitoring volumes (`prometheus-data`, `grafana-data`, `loki-data`, `influxdb-data`) | Docker volumes | Optional. Metrics history only; dashboards are provisioned from the repository. |

Redis holds only rate limits, revoked tokens, queues and caches; it is not backed up.

## Backing up the database

Dump through the `db` container; it works while the stack is running:

```bash
cd /opt/skylab/app
set -a; . ./.env; set +a
docker compose exec -T db pg_dump -U "$POSTGRES_USER" -Fc "$POSTGRES_DB" > "skylab-$(date +%F).dump"
docker compose exec -T db pg_dump -U "$POSTGRES_USER" -Fc litellm > "litellm-$(date +%F).dump"   # AI stack only
```

`-Fc` produces a compressed custom-format archive that `pg_restore` can replay selectively. Copy the dumps together with `.env` and `vllm-service/litellm/.env` to a location outside the server, and keep `.env` as carefully as the dump: it contains the key.

A nightly cron entry on the host is enough for a campus deployment:

```cron
30 3 * * * cd /opt/skylab/app && set -a && . ./.env && set +a && docker compose exec -T db pg_dump -U "$POSTGRES_USER" -Fc "$POSTGRES_DB" > /var/backups/skylab/skylab-$(date +\%F).dump
```

Alternatively stop the stack and copy the volume (`docker run --rm -v app-db-data:/data -v "$PWD":/out alpine tar czf /out/app-db-data.tgz -C /data .`); a volume copy is only consistent when the database is stopped.

## Restoring the database

1. Restore `.env` (same `SECRET_KEY`) and the repository checkout at the commit the dump was taken from, or a newer one.
2. Start only the database:

   ```bash
   docker compose up -d db
   ```

3. Replace the database contents:

   ```bash
   set -a; . ./.env; set +a
   docker compose exec -T db psql -U "$POSTGRES_USER" -d postgres -c "DROP DATABASE IF EXISTS \"$POSTGRES_DB\";" -c "CREATE DATABASE \"$POSTGRES_DB\";"
   docker compose exec -T db pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --no-owner < skylab-2026-10-18.dump
   ```

4. Start the rest. `prestart` applies any migrations newer than the dump, then the backend comes up:

   ```bash
   docker compose up -d
   docker compose logs -f prestart
   ```

5. Log in, open "PVE connections" and press **Test** on each connection. If the test fails with a decryption error, the `SECRET_KEY` in `.env` is not the one the dump was encrypted with.

Restore the `litellm` database the same way when the AI stack is in use, then `bash scripts/prepare-ai-stack.sh --start`.

## After a restore

- Machines on Proxmox are unaffected by a platform restore. Anything created or deleted between the dump and the restore is out of sync: the "PVE connections" page's **Sync** reconciles the list of guests, and the Resource Management page shows machines SkyLab knows but PVE does not.
- Requests approved after the dump are lost; their machines, if already built, appear as unmanaged guests.
- Everyone has to log in again (Redis is empty).
- Re-sync the gateway from the "Gateway VM" page so nginx rules and WireGuard peers match the restored database.

## Machine backups

Per-machine backups and snapshots are created from the machine's detail page and stored on the Proxmox storage configured for backups on the connection. They are Proxmox `vzdump` archives tagged by SkyLab and are deleted together with the machine. They are not part of the platform backup; include the Proxmox backup storage in your Proxmox backup plan.

## Disaster recovery checklist

1. New server with Docker, same host name or an updated `FRONTEND_HOST`.
2. Clone the repository, restore `.env` and the LiteLLM files.
3. Restore the database (above), start the stack, check `GET /api/v1/utils/health-check/ready`.
4. Test every PVE connection; sync.
5. Re-sync the gateway; verify the platform entry answers over HTTPS.
6. Re-run the AI stack helper if models are used.
